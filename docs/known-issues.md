# 已知问题（v0.1.0）

按影响排序。每条都写明「现在是什么行为」，不写「可能会」。

## 1. Windows 可执行文件未代码签名

首次运行可能被 SmartScreen 或第三方杀毒软件提示「未知发布者」。核对 Release 页的 SHA256 后自行决定放行。没有做签名是因为 v0.1.0 没有代码签名证书，伪造一个签名更糟。

## 2. systemd 验收在 runner 上完成，未覆盖独立虚拟机

v0.2.1 起 CI 在 `ubuntu-22.04` 与 `ubuntu-24.04` 两个 runner 上跑完整生命周期（两者的 PID 1 都是 systemd）：安装 → `systemctl enable --now` → 页面工作流 → `kill -9` 后由 systemd 拉起 → 卸载保留数据 → 重装保留历史。另有一个 Debian 12 容器作业，只验证安装与二进制兼容性，**不验证 systemd**（容器没有 init），作业日志里会打印这条限制。

**没有**在独立的 Ubuntu 24.04 / Debian 12 虚拟机上验证。Debian 12 的 systemd 生命周期属于未验证项。

## 3. Linux 只发布 x64

ARM64 需要单独构建（SEA 的注入目标必须是运行平台的 node 二进制）。v0.1.0 未提供，按需求「不以未完成 ARM64 阻断首版」处理。

## 4. 远程访问需要显式声明信任的域名

`--host 0.0.0.0` 只扩大监听范围，不扩大信任范围：浏览器实际访问的域名或 IP 必须写进 `AI_DEBATE_TRUSTED_HOSTS`（逗号分隔），否则读取配置会得到 `403 forbidden: origin`。默认只信任回环名，且不会从 `Host` 头推断。这是刻意的取舍，代价是远程部署多一行配置。

## 5. 没有内置 TLS

`--host 0.0.0.0` 可以直接用，但口令会走明文 HTTP。远程访问必须自行加 Nginx/Caddy 反代，`docs/security.md` 说明了反代必须保留 `Host`/`Origin` 的原因。

## 6. 真实发表能力未在本环境实测

贴吧的真实发表需要有效 Cookie 与真实账号，v0.1.0 的验收在离线导入链路上完成（导入 → 分析 → 生成 → 编辑 → 批准 → 复制）。发表路径的代码与门禁未改动，但**没有在真实平台发出过一条回复**。未验证的平台能力在界面上保持「不可用」，不会出现可点的发表按钮。

## 7. 微博平台依赖外部 CLI

原插件通过官方 CLI 读取微博，独立版没有打包这个 CLI。因此微博路径在没有安装该 CLI 的机器上会显示「不可用」，而不是假装可用。贴吧的 HTTP 读取不受影响。

## 8. Agent 工具没有调用入口

9 个 `debate_*` 工具仍被注册到内存中的工具表，但独立版没有 agent。将来接 MCP 时可直接复用。当前它们的存在只体现在系统页的计数上。

## 9. 单实例限制

同一个数据目录只允许一个进程。第二个 `serve` 会发现记录并退出（退出码 3，提示已有实例的地址）。这不是内核级互斥：删掉 `run/instance.lock` 仍可强开第二个进程，那是留给误判的逃生口。

## 10. 登录限流计数在内存里

限流窗口是进程内计数，重启后清零。这不是可被绕过的漏洞（重启需要本机权限），但意味着攻击者若能反复触发重启，限流就不连续。没有落盘是因为写磁盘本身会成为登录路径上的放大点。

## 11. 单管理员、无多用户

只有一个管理员账号，没有角色与权限分级。多人共用一台机器时，所有人都拥有全部权限。

## 12. 密码重置需要手动操作

忘记密码时：停服务 → 删除 `admin.json` → 重启 → 重新初始化。没有「邮件重置」这类流程，因为这是单机产品，没有可用的外发通道。

## 13. 队列只承载维护类任务

备份、恢复、日志轮转、凭据审计、存储自检。分析/生成/发表**没有**排进队列：分析需要人工在页面操作，发表不可重试。因此「关掉浏览器后继续跑一次分析」在 v0.1.0 不成立。

## 14. 审计日志未做防篡改

`logs/audit.jsonl` 是普通追加文件。能写数据目录的人可以改它。没有做签名链。

## 15. 备份不含凭据

这是刻意的，但意味着换机器恢复后必须重新填 API Key 与 Cookie。文档已说明。

## 16. 原插件的 234 个测试未全部迁移

只迁移了不依赖宿主核的部分（111 个断言）。`test/cordis-integration.test.ts` 之类测的是 DSH 集成，不再适用，已删除；其余与页面相关的测试由新的前端测试覆盖。

## 17. 后台监控的读取范围是有界的

默认每次只读首页与最后两页，每楼最多 3 页嵌套、12 个楼中楼；补偿扫描另有一次 8 页上限。这是把一轮轮询的请求数压到可接受范围的代价：

- **在窗口之外被编辑或删除的旧回复不会被发现。** 补偿扫描默认回看 24 小时（可配 1–168 小时），更早的变化需要手动「全量重查」。
- **全量重查也受 `maxFloorPages` 限制**（默认 60 页）。超出时会明确报告「未覆盖」，不会假装读完。

轮询间隔最低 120 秒，且不会因为积压而缩短——这是刻意服从平台限制。

## 18. 后台监控未在真实账号上验证

自动化链路用脚本化平台做过端到端验证（发现→分析→生成→待审核、限流退避、认证失效暂停、崩溃恢复、分页与游标、长时间运行的堆增长）。

**没有**用真实贴吧/微博账号跑过长期轮询。2026-11-20 的一次匿名只读检查（`scripts/check-platform.mjs`）在构建网络上得到的是平台拒绝/空页，未取得可用读数——见 `docs/acceptance-v0.2.1.md` §真实平台。真实平台的可读性、限流阈值、嵌套回复结构仍需实号验证，未验证的能力在界面上保持 `unavailable`。

## 18.1 24 小时连续运行未在本机跑满

压力测试脚本 `test/stress/soak.ts` 支持 `--seconds=86400`，CI 跑 5 分钟、本机跑 40–120 秒。已测的是「压缩后的高迭代次数下堆不增长、候选不重复、台账有界」，**没有**跑满 24 小时墙钟。这一点在验收记录里单独标注，不计为已完成。

## 18.2 开机自启的写入路径在受限主机上无法验证

Windows 的自启由 `reg.exe` 写入 `HKCU\...\Run`（值为 `"<exe>" --no-browser`）。在本项目的构建机上，`reg.exe` 被主机的程序黑名单拦截，因此验收把这一步如实标为「环境限制，未计为通过」，而不是伪造成功。产品侧的行为是：写入失败时返回可读的 400，不会报告成功。

## 19. 「运行状态」页签首次打开较慢

该页签会真实探测一次平台能力（含微博 CLI 是否可用），在没有安装 CLI、且出网受限的机器上大约需要 9 秒。它只在用户点开这一页时发生，不影响登录、配置保存与工作流。顶部状态灯与 `/system` 页走的是轻量接口，不受影响。

## 20. 页面文案仍有少量「插件」措辞

由于页面是从原插件逐字继承的，个别提示语里仍会出现「插件」「本部署」这类词。功能不受影响，措辞在后续版本统一。
